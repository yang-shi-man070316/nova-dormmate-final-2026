# ｜A模块：一次问题完整处理闭环
> 业务流程：**发现异常 → 判断优先 → 采取动作 → 验证效果 → 记录复盘**

## 测试环境
- 监测节点：`dorm-a`、`dorm-b`、`dorm-c`
- MQTT服务：Mosquitto WebSocket，地址 `ws://127.0.0.1:8083`
- 前端页面
  - `A2.html`：Dashboard监控面板，事件处理页面
  - `report.html`：统计报告 + A4事件复盘页面
- 数据存储：浏览器 `localStorage`
  > 规则：**只有事件闭环、环境恢复正常之后，才会写入事件记录**

## A1｜哪个宿舍现在最值得关注？
### 优先判断规则
1. 第一优先级：对比**连续异常时长**，时长更长优先
2. 第二优先级：异常次数，次数多优先
3. 相同条件：按nodeId固定顺序

### 本次测试场景
- `dorm-a`：状态正常
- `dorm-b`：连续多次偏热
- `dorm-c`：仅单次偏湿

✅ 系统判定：优先关注 `dorm-b`
> 原因：dorm-b连续异常持续时间更长

## A2｜发现问题以后，我能做什么？
1. MQTT接收报文，`dorm-b`上报状态：**偏热**
2. 用户在Dashboard页面点击【开启风扇】
3. 系统更新事件状态为「处理中」，**记录操作动作与操作时间**
4. 页面实时展示事件，提示仍在处理
> ⚠️ 关键点：点击开启风扇**不等于问题解决**，需要等待后续数据验证

## A3｜处理以后，真的变好了吗？
1. 用户操作完成后，系统持续接收MQTT温湿度数据
2. 发送新报文：`dorm-b` 温度25℃，湿度55%，状态正常
3. **依靠新收到的数据自动判断恢复，不能通过按钮直接标记完成**
4. 事件状态从「处理中」更新为「已恢复」

## A4｜把一次问题完整保存，用于复盘
1. 事件闭环完成后，整套事件自动存入 `localStorage`
2. 存储字段：宿舍编号、异常开始时间、异常问题、优先原因、处理动作、操作时间、恢复时间、最终结果
3. `report.html`读取本地存储，渲染【事件复盘表格】
4. 完整链路可回看：发现异常 → 判断优先 → 采取动作 → 验证恢复，完成业务闭环

### 本次完整事件示例
> 20:30｜dorm-b｜连续偏热
> → 20:35｜优先关注dorm-b（连续异常时间更长）
> → 20:40｜开启风扇
> → 20:55｜收到新数据，温湿度恢复正常
> → 21:10｜事件结束，保存至复盘记录

## B4｜项目页面分工说明

### 三个页面的职责
- `A2.html`：MQTT监控面板 —— 温湿度状态表格、设备控制与事件处理，包含B1实时总览、B2优先级判断、A4事件记录
- `3d.html`：3D宿舍可视化页面 —— 接收MQTT消息，3D模型根据状态自动变色（偏热→红、偏湿→蓝、正常→原色），含A1优先级面板
- `report.html`：历史事件页面 —— A4事件复盘表格 + B3今日温湿度历史摘要

### MQTT消息协同
- `A2.html` 与 `3d.html` 订阅**同一组MQTT主题**（环境数据 `dormmate/+/env` 等）
- 同一份报文到达时，两个页面**同时接收、独立响应**，互不影响：
  - A2.html：更新温湿度表格、执行恢复判断、驱动事件闭环
  - 3d.html：刷新对应宿舍的3D模型颜色
- `report.html` 不直接连接MQTT：A2事件闭环写入 `localStorage` 后，report页面读取数据展示复盘表格与今日摘要
